# 実装メモの追記

機能の実装が一段落したら、該当する `Docs/features/NN-*.md` の末尾に「実装メモ」を追記する。
ルールは **「地図であって写経ではない」**。コードを読めば分かることは書かず、どこを見ればよいか・なぜそうしたかだけを残す。

## 手順

1. 対象の機能ファイルを特定する（今回触った機能。複数あれば機能ごとに書く）
2. 差分を確認する: `git status` と `git diff`（コミット済みなら `git log` / `git show` で該当コミット）
3. 対象ファイルを読み、「仕様」「決定事項」「関連ファイル」と重複しないようにする
   - 仕様や決定事項そのものが変わった場合は、実装メモではなくその節を直接更新する
4. ファイルの末尾に下のフォーマットで追記する（既に「実装メモ」があれば、その節を更新する。節を増やさない）
5. 完了なら先頭の `status: 完了` と `completed`（今日の日付 `YYYY-MM-DD`）を更新する
6. 追記した内容をユーザーに短く報告する。コミットはユーザーに頼まれたときだけ

## フォーマット

```markdown
## 実装メモ

- 変更: どのファイル／クラスに何の責務を持たせたか（1〜3 行）
- 設計判断: 迷った点と選んだ理由（「決定事項」にない、実装中の小さな判断）
- 注意点: 次に触る人（未来の自分）が踏みそうな罠・依存関係・インスペクター設定
- 動作確認: 何をどう確認したか／未確認のこと
```

## ルール

- 節全体（見出しを含む）で **15 行以内**
- 「地図であって写経ではない」
  - コードの貼り付け・処理の逐一説明・行ごとの解説はしない
  - クラス名・メソッド名・ファイル名は書いてよい（`Car.Tick` のように場所を示す目的で）
  - 数値の初期値はインスペクターにあるので書かない（意味のある根拠があるときだけ書く）
- 書くことがない項目は省略してよい（無理に埋めない）
- 動作確認は Claude が Unity エディタを操作できないため、ユーザーが確認したこと／まだ確認していないことを正直に書く。不明ならユーザーに聞く
- 日本語で書く
